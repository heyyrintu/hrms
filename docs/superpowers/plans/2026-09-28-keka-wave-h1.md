# Keka Wave H1 — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.
> Execution method (set by the user): one scaffold commit, then three
> implementers in parallel on disjoint files (mid-tier model), one review per
> workstream, one whole-branch review, one fix wave. Steps use `- [ ]`.

**Goal:** Per-tenant Google/Microsoft SSO, TOTP two-factor authentication with
recovery codes and per-role enforcement, and additive custom roles checked by
the existing `RolesGuard`.

**Architecture:** `RolesGuard` accepts a route when the fixed role matches
`@Roles` (unchanged) or the user's custom roles hold a permission named by the
new `@RequirePermissions`. Custom-role permissions are loaded per request in
`validateUser`, never stored in the JWT. Password login becomes a small state
machine that can hand back short-lived `typ`-tagged step tokens; the JWT
strategy rejects any token with `typ`, so every existing session stays valid.
SSO runs the OIDC code flow on the API (PKCE + state + nonce in the DB) and
gives the browser only a single-use exchange code in the URL fragment.

**Tech stack:** NestJS 11, Prisma, PostgreSQL, `openid-client@5` (CommonJS),
`otplib@12`, `qrcode`; Next.js 16 / React 19, axios, react-hot-toast.

**Spec (binding):** `docs/superpowers/specs/2026-09-28-keka-wave-h1-design.md`
**Branch / worktree:** `feat/keka-wave-h1` at `.claude/worktrees/wave-h1`.

## Review Focus

Inputs the spec implies but its tests would not naturally hit. Each has a test
in the owning task.

1. **`/login?org=acme` with a password** must sign into tenant `acme`, not the
   default tenant. SSO already honours `org`, so the password form must too
   (`LoginDto.tenantCode`, WS-2 Task 2.3).
2. **IdP email casing differs** from the stored email
   (`Priya.S@Acme.com` vs `priya.s@acme.com`) → still matches the same user
   (WS-3 Task 3.4).
3. **Recovery code typed differently**: upper case, with spaces, without the
   dash → accepted once (WS-2 Task 2.1).
4. **Setup called twice** (user reloads and rescans): only the newest QR's
   codes enable 2FA; the old one fails (WS-2 Task 2.4).
5. **Reload or back on `/sso/callback`** after the code was used → the login
   page with a readable error, not a blank page or a redirect loop (WS-3 Task 3.6).

    const targets = [context.getHandler(), context.getClass()];
    const requiredRoles = this.reflector.getAllAndOverride<UserRole[]>(ROLES_KEY, targets);
    const requiredPermissions = this.reflector.getAllAndOverride<string[]>(PERMISSIONS_KEY, targets);
    const hasRoles = !!requiredRoles && requiredRoles.length > 0;
    const hasPermissions = !!requiredPermissions && requiredPermissions.length > 0;
    if (!hasRoles && !hasPermissions) return true;

    const user = context.switchToHttp().getRequest().user as AuthenticatedUser | undefined;
    if (!user) return false;
    if (user.role === UserRole.SUPER_ADMIN) return true;
    if (hasRoles && requiredRoles.includes(user.role)) return true;
    // Custom roles only widen access on routes that opt in with @RequirePermissions.
    if (hasPermissions) {
      const held = user.permissions ?? [];
      return requiredPermissions.some((p) => held.includes(p));
    }
    return false;
  }
